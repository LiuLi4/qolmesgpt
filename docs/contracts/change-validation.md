# 变更验证规范

## 用途

约束从故障证据到代码变更的验证闭环，避免模型仅凭日志猜测根因或在未审批时修改仓库。

## 从 base 推导出的设计后果

项目同时提供 CLI、HTTP 服务和多种外部 Toolset，因此每个可观察行为都要有明确入口、证据来源和可重复的测试门，不能只依赖一次模型回复。

## 架构不变量

- 根因结论必须引用实际工具结果，并区分事实、推断和待验证假设。
- 代码修改前必须形成可审阅的修复方案和变更范围。
- GitLab 写操作、提交和 MR 创建必须位于人工审批之后。
- 修复验证应覆盖回归测试、相关集成行为和必要的 staging 观测结果。
- 失败或无数据时，流程应返回当前阶段、已尝试的证据和下一步可执行动作。

## 品味不变量

- 方案和验证结果应短而具体，包含文件、命令、测试和外部资源标识。
- 不把模型推测写成已验证事实。
- 每个副作用都应能追踪到触发它的审批和工具调用。

## 本地自由

具体的测试框架、MR 模板、分支命名和审批系统可沿用项目或组织已有约定；只要保留审批前后边界和可回滚证据。

## 校验方式

Spec 的 BDD 场景应覆盖成功、无数据、权限失败、测试失败和审批拒绝。实现阶段执行 `docs/base/testing.md` 中的测试门，并在提交前检查 Git diff 与工作树状态。

## 反馈闭环

每次修复验证发现的新边界应更新相关 spec；重复出现的漏检应转化为自动化测试或结构校验。

## 不覆盖

不定义具体 GitLab API 调用、模型供应商、代码审查人员和生产发布窗口。
