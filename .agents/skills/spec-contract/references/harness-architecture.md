# 通用 Harness 架构与品味基线

## 目标

通过强制不变量，而不是微观管理实现过程，让 AI 快速交付且不削弱架构基础。

## 使用方式

每次生成 contract，先把这里当作通用架构与品味底座，再叠加 base 文档、技术栈和现有代码事实。
如果项目偏离这里的基线假设，先判断偏离是否来自技术栈或项目历史，再写成适合本项目的规范。

## 约束模型

- 中央层应当强制边界、正确性和可重复性。
- 本地层应当保留表达自由，不规定具体库调用和微观实现。
- 约束应当落到不变量，而不是落到编码过程。
- 可机械检查的部分应当交给工具，文档负责说明取舍。

## 架构不变量

- 边界处应当解析数据形状，再把稳定形状传给内部代码。
- 依赖方向应当可预测，并能通过 lint 或结构测试验证。
- 业务域存在固定层次时，应当只允许有限依赖边。
- 横切关注点应当通过单一显式入口进入，例如 Providers 或项目已有等价接口。
- 状态、配置、IO 和外部副作用应有可追踪归属。

## 品味不变量

- 代码应该容易从一个小切口进入，并能顺着文件名、索引和测试找到下一步。
- 依赖关系应当清楚、稳定、可测试；复杂技巧不应压过结构清晰。
- 不透明依赖应当在降低调用方复杂度时包一层，否则不新增封装。
- 错误信息和测试失败应给出修复线索。
- 新增实体要有明确职责，避免只为了分层而分层。
- 生成代码不必完全符合人类个人偏好，但应正确、可维护，并让未来智能体清晰可读。

## 校验原则

- 中等约束写应当、不应和允许例外的条件。
- 强校验依赖技术栈已有测试框架、类型系统、lint、结构测试、构建和 CI。
- 如果某条规则反复靠人工提醒，应当考虑把它转成测试或工具。
- 自定义 lint 和结构测试的错误信息应在智能体情境中给出修复指令。
- contract 不列命令清单；命令来源仍然是 base/testing.md 或项目脚本。

## 反馈闭环

- 审查评论、重构 PR 和用户可见 bug 应当反馈为文档更新或工具规则。
- 当文档不足以阻止漂移时，应当把规则转化为代码、lint 或结构测试。
